# Contract tree (generated)

`contracts/` is a **derived artifact**. It holds one markdown contract per
*enabled* omnicli tool, grouped by skill, and is produced from the same
catalog rows that power `omnicli describe`. No file under `contracts/` is
hand-authored or hand-edited — edit the skill/catalog source and regenerate.

## Layout

```
contracts/
  INDEX.md                     skill -> directory map (with per-skill counts)
  <skill>/
    <tool>.md                  name, when-to-use, input schema, one example
```

Each contract file contains four sections: `## Name`, `## When to use`,
`## Input schema` (a JSON code block), and `## Example` (a bash command).
Every file carries the marker `<!-- generated by contract_tree.py — DO NOT
EDIT -->`; the generator only prunes stale files that carry this marker, so
unrelated files placed under `contracts/` are left alone.

## Regenerate

Run the generator from the repo root (no arguments needed):

```bash
python3 orchestration/omnicli/catalog/contract_tree.py
```

The generator reads the built catalog read-only, so regeneration is
deterministic: two runs produce byte-identical files. Useful modes:

```bash
python3 orchestration/omnicli/catalog/contract_tree.py --list    # enabled tool ids, one per line
python3 orchestration/omnicli/catalog/contract_tree.py --hash    # sha256 of the generated tree
python3 orchestration/omnicli/catalog/contract_tree.py --check   # exit 1 if on-disk tree drifted
```

When the catalog has not been built yet the generator builds it once from the
skill tree, then proceeds. Re-run after any tool/policy change. If a file is
wrong, fix the catalog source (or the generator) and regenerate — never patch
a file under `contracts/` directly; a later regeneration would overwrite it.

## Sandbox helpers (`contract_fs.mjs`)

`orchestration/omnicli/catalog/contract_fs.mjs` exposes the tree to Code Mode
plans without leaving the sandbox. It uses only `node:fs` / `node:path` /
`node:url`; no subprocesses, no network. Paths are confined to `contracts/`.

```js
import { ls, read } from "./orchestration/omnicli/catalog/contract_fs.mjs";

ls();                          // ["INDEX", "academic-icm", ...] (skills)
ls("academic-icm");            // tool names in that skill
read("academic-icm/cli", "name");              // "academic-icm/cli"
read("academic-icm/cli", "name+description");  // { name, description }
read("academic-icm/cli", "full");              // { name, description, inputSchema, example, raw }
```

`read(path, detail)` mirrors the Anthropic `search_tools` detail levels as a
filesystem read:

- `name` — just the tool name/id.
- `name+description` — name plus its when-to-use blurb.
- `full` — the parsed contract (name, description, input schema, example) and
  the raw markdown.

The module locates `contracts/` by walking up from its own file (resolving
symlinks), so it works from the repo root or the `omnicli` shim. In a `strict`
sandbox that masks `$HOME`, stage the tree into the workspace and set
`OMNICLI_CONTRACTS_ROOT` to its location; the `write`/`none` sandbox modes see
the repo tree at its normal path.
